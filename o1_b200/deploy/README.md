## Frozen execution constraints

Scientific execution is **BF16 PyTorch/Transformers, eager attention** — the
sealed generator's exact configuration. The following are **absent by
design**: FP8, FP4, quantization, speculative decoding, vLLM, TensorRT-LLM,
SGLang, altered sampling, altered attention semantics, changed prompts,
changed stopping rules.

Optional performance modes (`torch_compile`, `cuda_graphs`,
`attention_override`, batched `compaction`) exist behind RuntimeConfig flags
that **default OFF**; `RuntimeConfig.validate()` refuses the first three
outright, and every one of them remains scientifically ineligible until a
future, separately committed hardware equivalence pass authorizes it.

sm_103 (B300) native execution rests on NVIDIA's documented
same-major/higher-minor SASS forward-compatibility rule: the cu130 wheel's
sm_100 cubins run natively on sm_103, plus 59 sm_103a arch-tuned kernels; the
wheel embeds NO PTX, so silent JIT fallback is impossible. This is now
backed by direct `cuobjdump` evidence, not just the documented rule — see
`FATBINARY_ARCH_EVIDENCE.json` above.

`hardware_gate.py` compares the CUDA runtime and driver versions numerically
(parsed into version tuples, e.g. `(13, 0)`), not lexicographically, because
a naive string compare would wrongly accept a single-digit-major runtime
(`"9.0" >= "13.0"` is true as strings, false as versions); the driver floor
is r580 for the CUDA 13.0 runtime.

## HF offline scoping

The pod keeps `HF_HUB_OFFLINE=1` set for the whole scientific process, so
model/tokenizer loading provably cannot reach the network. The Hugging Face
hub is reachable ONLY through the isolated `runner/hf_transfer.py`
subprocess helper (the Foundation Learner package carries its own copy),
which is spawned with the offline flags stripped and refuses loudly if
`HF_HUB_OFFLINE` survives into the subprocess; every transfer through it is
SHA-256 digest-verified end to end.
